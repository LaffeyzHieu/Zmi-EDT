     1→     1→# Zmi EDT — Product & Engineering Specification
     2→     2→## Version 0.1 — Batch Image Editor
     3→     3→
     4→     4→> **Purpose:** This document is the source of truth for implementing Zmi EDT.
     5→     5→> Build incrementally. Do not attempt to implement every feature in one pass.
     6→     6→> After each milestone, run/build/test the application before moving on.
     7→     7→
     8→     8→---
     9→     9→
    10→    10→## 1. Product Goal
    11→    11→
    12→    12→Zmi EDT is a browser-based image editor designed around a specific workflow:
    13→    13→
    14→    14→- Import many images by drag & drop.
    15→    15→- Display each image as an independent floating editor window.
    16→    16→- Choose one window as **MAIN**.
    17→    17→- Editing MAIN can broadcast supported actions to all currently active batch windows.
    18→    18→- Any individual window can be edited independently.
    19→    19→- Windows can be temporarily excluded from batch operations without deleting them.
    20→    20→- Inspect the whole workspace or temporarily hide editor chrome with **Ngắm waifu** mode.
    21→    21→- Export one image, all images, or the active batch as individual PNG files or a ZIP.
    22→    22→
    23→    23→The product is **not** intended to become Photoshop. Prioritize reliability, predictable state, and the batch workflow.
    24→    24→
    25→    25→### Primary use case
    26→    26→
    27→    27→The user has many images with the same aspect ratio and wants to normalize/edit them together while retaining the ability to make per-image corrections.
    28→    28→
    29→    29→---
    30→    30→
    31→    31→# 2. Design Principles
    32→    32→
    33→    33→1. **Batch operations must be explicit and predictable.**
    34→    34→2. **Individual edits must never unexpectedly modify other windows.**
    35→    35→3. **MAIN is the source of batch actions.**
    36→    36→4. **Excluded windows remain in the workspace but do not receive MAIN batch actions.**
    37→    37→5. **Every meaningful edit must be undoable.**
    38→    38→6. **Do not destroy source data unnecessarily.**
    39→    39→7. **Do not add large features unless they support the core workflow.**
    40→    40→8. **Prefer deterministic pixel/coordinate behavior over clever automatic behavior.**
    41→    41→9. **Keep modules/components separated so one feature can be implemented without rewriting unrelated features.**
    42→    42→10. **The application must remain usable even when a later feature is unfinished.**
    43→    43→
    44→    44→---
    45→    45→
    46→    46→# 3. Workspace Model
    47→    47→
    48→    48→The application contains a workspace with zero or more image windows.
    49→    49→
    50→    50→Each window represents one imported image/document.
    51→    51→
    52→    52→A window has at least:
    53→    53→
    54→    54→```text
    55→    55→Window
    56→    56→- id: unique internal ID
    57→    57→- fileName
    58→    58→- sourceImage
    59→    59→- canvas/document state
    60→    60→- position: x, y (workspace coordinates)
    61→    61→- size: window width/height
    62→    62→- isMain: boolean
    63→    63→- isBatchEnabled: boolean
    64→    64→- isSelected: boolean
    65→    65→- layers
    66→    66→- history
    67→    67→```
    68→    68→
    69→    69→### Window lifecycle
    70→    70→
    71→    71→```text
    72→    72→Drag/drop image
    73→    73→    ↓
    74→    74→Create window
    75→    75→    ↓
    76→    76→Window becomes available in workspace
    77→    77→    ↓
    78→    78→User can:
    79→    79→    - move it
    80→    80→    - select it
    81→    81→    - exclude/include it in batch
    82→    82→    - make it MAIN
    83→    83→    - edit it
    84→    84→    - close/delete it
    85→    85→```
    86→    86→
    87→    87→Closing a window removes it from the current workspace. It should not silently delete the original uploaded asset from the uploaded-file library.
    88→    88→
    89→    89→---
    90→    90→
    91→    91→# 4. Import / Drag & Drop
    92→    92→
    93→    93→## Required behavior
    94→    94→
    95→    95→The user can drag supported image files into the application.
    96→    96→
    97→    97→There are two distinct import semantics:
    98→    98→
    99→    99→### Drop onto workspace
   100→   100→
   101→   101→- A supported image dropped onto an empty workspace is imported as a **new document/window**.
   102→   102→- Multiple files dropped at once create multiple windows.
   103→   103→
   104→   104→### Drop onto an existing window
   105→   105→
   106→   106→- A supported image dropped onto an existing window is imported as a **new image layer/element in that window**.
   107→   107→- It must NOT create another editor window.
   108→   108→- The target window should visibly indicate that it is the current drop target.
   109→   109→
   110→   110→The UI should also provide a `+` control on each window for adding an asset/layer without drag & drop. At minimum:
   111→   111→
   112→   112→```text
   113→   113→+
   114→   114→├── Import image as layer
   115→   115→├── Add text
   116→   116→└── Create empty layer
   117→   117→```
   118→   118→
   119→   119→Importing a layer is local by default, including when the target is MAIN. It does not automatically broadcast to the batch. If the user wants the new layer applied to the batch, that must be an explicit batch action.
   120→   120→
   121→   121→## Initial supported formats
   122→   122→
   123→   123→At minimum:
   124→   124→
   125→   125→- PNG
   126→   126→- JPG/JPEG
   127→   127→- WebP
   128→   128→
   129→   129→SVG can be added later if the rendering architecture supports it cleanly.
   130→   130→
   131→   131→## Same-ratio assumption
   132→   132→
   133→   133→The primary workflow assumes images use the same aspect ratio.
   134→   134→
   135→   135→The editor does not need to automatically normalize arbitrary aspect ratios in v0.1.
   136→   136→
   137→   137→If an image has a different ratio, warn the user rather than silently stretching it.
   138→   138→
   139→   139→## Important
   140→   140→
   141→   141→Never modify the original uploaded file merely because the user edits the canvas.
   142→   142→
   143→   143→The document should have its own editable state.
   144→   144→
   145→   145→---
   146→   146→
   147→   147→# 5. Window Controls
   148→   148→
   149→   149→Every image window has:
   150→   150→
   151→   151→- title / filename
   152→   152→- `_` control
   153→   153→- `X` control
   154→   154→
   155→   155→## `X` — Close window
   156→   156→
   157→   157→Removes the window from the workspace.
   158→   158→
   159→   159→If the window is not MAIN:
   160→   160→- close immediately or with a lightweight confirmation if unsaved changes are involved.
   161→   161→
   162→   162→If the window is MAIN:
   163→   163→- show a confirmation dialog.
   164→   164→
   165→   165→Suggested message:
   166→   166→
   167→   167→> Are you sure?
   168→   168→> This window is currently MAIN. Closing it will remove it from the batch workspace.
   169→   169→
   170→   170→After MAIN is removed:
   171→   171→- choose another eligible active window as MAIN automatically if possible.
   172→   172→- otherwise MAIN becomes null.
   173→   173→
   174→   174→Never leave the application in an invalid state.
   175→   175→
   176→   176→## `_` — Toggle batch participation
   177→   177→
   178→   178→This is NOT a normal minimize button.
   179→   179→
   180→   180→It means:
   181→   181→
   182→   182→> Toggle whether this window participates in MAIN batch operations.
   183→   183→
   184→   184→When excluded:
   185→   185→- keep the window visible.
   186→   186→- keep all its edits/state.
   187→   187→- do not delete it.
   188→   188→- do not apply future MAIN batch operations to it.
   189→   189→
   190→   190→The UI should visibly indicate excluded state.
   191→   191→
   192→   192→Example:
   193→   193→
   194→   194→```text
   195→   195→ACTIVE
   196→   196→Window participates in batch.
   197→   197→
   198→   198→EXCLUDED
   199→   199→Window remains open but does not participate in batch.
   200→   200→```
   201→   201→
   202→   202→---
   203→   203→
   204→   204→# 6. Selection
   205→   205→
   206→   206→There are two concepts:
   207→   207→
   208→   208→### Selected window
   209→   209→The window currently being inspected/edited.
   210→   210→
   211→   211→### MAIN window
   212→   212→The master window whose supported actions can be broadcast.
   213→   213→
   214→   214→They are not necessarily the same concept internally, although selecting MAIN may also select it.
   215→   215→
   216→   216→Only one window may be MAIN.
   217→   217→
   218→   218→Only one window should normally be the active editing target at a time.
   219→   219→
   220→   220→---
   221→   221→
   222→   222→# 7. MAIN
   223→   223→
   224→   224→MAIN is the core concept of the application.
   225→   225→
   226→   226→The MAIN window receives a strong visual indicator, such as a highlighted border and/or `MAIN` badge.
   227→   227→
   228→   228→Example:
   229→   229→
   230→   230→```text
   231→   231→┌─────────────────────────┐
   232→   232→│ ★ MAIN              _ X │
   233→   233→│                         │
   234→   234→│          image          │
   235→   235→│                         │
   236→   236→└─────────────────────────┘
   237→   237→```
   238→   238→
   239→   239→## Selecting MAIN
   240→   240→
   241→   241→The `Chọn MAIN` feature lets the user choose the current MAIN window.
   242→   242→
   243→   243→Selecting another window as MAIN:
   244→   244→- removes MAIN state from the previous window.
   245→   245→- adds MAIN state to the new window.
   246→   246→- updates the visual highlight.
   247→   247→- does not alter image content.
   248→   248→
   249→   249→## MAIN batch rule
   250→   250→
   251→   251→MAIN is the reference document for creating batch actions, but MAIN does **not** mean that every edit to the entire image is automatically copied.
   252→   252→
   253→   253→For a batchable operation, the user selects a specific layer/element as the target. The resulting action is then applied to the corresponding target in all batch-enabled windows.
   254→   254→
   255→   255→```text
   256→   256→MAIN
   257→   257→  ↓
   258→   258→select target layer/element
   259→   259→  ↓
   260→   260→perform batchable action
   261→   261→  ↓
   262→   262→create ONE batch action
   263→   263→  ↓
   264→   264→apply to corresponding target in all batch-enabled windows
   265→   265→```
   266→   266→
   267→   267→Example:
   268→   268→
   269→   269→```text
   270→   270→MAIN → select `Character` → Move X +3px, Y -1px
   271→   271→
   272→   272→A Character       +3, -1
   273→   273→B Character       +3, -1
   274→   274→C Character       +3, -1
   275→   275→D Character       +3, -1
   276→   276→E excluded        unchanged
   277→   277→```
   278→   278→
   279→   279→The batch target should therefore be explicit in the action model. Do not broadcast an ambiguous `Move` operation to an entire document unless the operation explicitly targets the canvas/document.
   280→   280→
   281→   281→Excluded windows do not receive the action.
   282→   282→
   283→   283→The MAIN itself is included.
   284→   284→
   285→   285→## Status indicator
   286→   286→
   287→   287→The workspace should show useful information such as:
   288→   288→
   289→   289→```text
   290→   290→6 windows · MAIN: claude.png · 5 in batch
   291→   291→```
   292→   292→
   293→   293→This is important because the user needs to know exactly how many documents will be affected.
   294→   294→
   295→   295→---
   296→   296→
   297→   297→# 8. Batch Semantics
   298→   298→
   299→   299→Not every action should automatically be batchable.
   300→   300→
   301→   301→Every action should declare whether it supports batch application.
   302→   302→
   303→   303→Suggested action categories:
   304→   304→
   305→   305→### Safe / naturally batchable
   306→   306→
   307→   307→- move selected layer/element
   308→   308→- scale selected layer/element
   309→   309→- rotate selected layer/element
   310→   310→- flip selected layer/element
   311→   311→- delete matching layer/element
   312→   312→- add text with identical parameters
   313→   313→- some layer operations
   314→   314→- some crop operations if explicitly confirmed
   315→   315→
   316→   316→### Batch target rule
   317→   317→
   318→   318→A batchable action should carry an explicit target, for example:
   319→   319→
   320→   320→```text
   321→   321→Action
   322→   322→├── type: MOVE
   323→   323→├── scope: BATCH
   324→   324→├── sourceWindowId: MAIN
   325→   325→├── targetType: LAYER
   326→   326→├── targetIdentity: Character
   327→   327→└── parameters: { x: +3, y: -1 }
   328→   328→```
   329→   329→
   330→   330→For v0.1, batch transforms operate on the **selected layer/element**, not the whole image by default.
   331→   331→
   332→   332→Target matching should use stable internal identity where possible. Layer name matching can be provided by Smart Batch as a more flexible matching strategy. If a corresponding target cannot be found, the application must not silently modify an unrelated layer.
   333→   333→
   334→   334→### Usually local-only
   335→   335→
   336→   336→- freehand drawing
   337→   337→- manual selection
   338→   338→- pixel-specific edits
   339→   339→- arbitrary brush strokes
   340→   340→
   341→   341→The UI must make batch behavior clear.
   342→   342→
   343→   343→A batch action should be represented as ONE logical history action, even though it affects many windows.
   344→   344→
   345→   345→Example:
   346→   346→
   347→   347→```text
   348→   348→MAIN:
   349→   349→Move +3px X
   350→   350→
   351→   351→History:
   352→   352→[BatchMove +3px]
   353→   353→
   354→   354→NOT:
   355→   355→
   356→   356→[Move window 1]
   357→   357→[Move window 2]
   358→   358→[Move window 3]
   359→   359→...
   360→   360→```
   361→   361→
   362→   362→This is essential for usable Undo.
   363→   363→
   364→   364→---
   365→   365→
   366→   366→# 9. Coordinate System
   367→   367→
   368→   368→The main editing workflow assumes equal aspect ratios.
   369→   369→
   370→   370→For transformations:
   371→   371→
   372→   372→- use absolute pixel values by default.
   373→   373→- do not silently convert a user-entered `+1px` into a percentage.
   374→   374→- maintain a clear document/canvas coordinate system.
   375→   375→
   376→   376→Example:
   377→   377→
   378→   378→```text
   379→   379→x = 120
   380→   380→y = 80
   381→   381→width = 512
   382→   382→height = 512
   383→   383→rotation = 0
   384→   384→```
   385→   385→
   386→   386→The UI should expose numeric values where precision matters.
   387→   387→
   388→   388→Pixel-perfect editing is an explicit product goal.
   389→   389→

   392→   392→# 10. Sidebar — `Di chuyển`
   393→   393→
   394→   394→Purpose:
   395→   395→
   396→   396→> Move editor windows in the workspace.
   397→   397→
   398→   398→This mode affects the WINDOW, not the image contents.
   399→   399→
   400→   400→Behavior:
   401→   401→- drag window → window moves.
   402→   402→- image coordinates remain unchanged.
   403→   403→
   404→   404→This separation is mandatory.
   405→   405→
   406→   406→The user must be able to move a floating window without accidentally moving the artwork inside it.

   454→   454→
   455→   455→Freehand drawing.
   456→   456→
   457→   457→Required:
   458→   458→
   459→   459→- brush/freehand stroke
   460→   460→- brush size
   461→   461→- color
   462→   462→- drawing on the currently selected window/layer
   463→   463→- undo/redo
   464→   464→
   465→   465→Optional later:
   466→   466→
   467→   467→- opacity
   468→   468→- hardness
   469→   469→- eraser
   470→   470→- pressure sensitivity
   471→   471→
   472→   472→## Batch rule
   473→   473→
   474→   474→Freehand drawing should be local by default.
   475→   475→
   476→   476→Do not automatically broadcast arbitrary mouse/stylus coordinates to other images.
   477→   477→
   478→   478→If batch drawing is ever added, it must be an explicit action.

   501→   501→
   502→   502→# 15. `Xóa`
   503→   503→
   504→   504→Delete the selected element/layer.
   505→   505→
   506→   506→Behavior:
   507→   507→
   508→   508→1. user selects an element.
   509→   509→2. presses delete or uses the tool.
   510→   510→3. element is removed.
   511→   511→4. operation creates an undo history entry.
   512→   512→
   513→   513→## Batch behavior
   514→   514→
   515→   515→If the element has a stable identity across documents, deletion can be batchable.
   516→   516→
   517→   517→If the element is arbitrary pixel content, do not assume matching structure across documents.
   518→   518→
   519→   519→## Smart Batch
   520→   520→
   521→   521→Smart Batch is an explicit matching mode for applying an action to semantically matching layers/elements across documents. It is especially useful when the same layer name exists in multiple images but internal layer IDs differ.
   522→   522→
   523→   523→Example:
   524→   524→
   525→   525→```text
   526→   526→Smart Batch
   527→   527→Apply to all matching layers: [ Background ]
   528→   528→Action: Delete
   529→   529→```
   530→   530→
   531→   531→Expected behavior:
   532→   532→
   533→   533→- find the `Background` layer in each eligible document.
   534→   534→- apply the requested action only to matching layers.
   535→   535→- do not rely on layer index/position alone.
   536→   536→- if a document has no match, leave it unchanged and report the missing target.
   537→   537→
   538→   538→Smart Batch must be an explicit user choice; normal batch editing remains target-based and predictable.
   539→   539→
   540→   540→## MAIN deletion
   541→   541→
   542→   542→If deleting an element from MAIN with batch enabled:
   543→   543→- if the action is batchable, warn that multiple images will be affected.
   544→   544→- require confirmation for destructive batch deletion if appropriate.
   545→   545→
   546→   546→Suggested dialog:
   547→   547→
   548→   548→> Are you sure?
   549→   549→> This action will affect 5 images.
   550→   550→

   552→   552→
   553→   553→# 16. `Cắt`
   554→   554→
   555→   555→The UI should distinguish:
   556→   556→
   557→   557→### Crop
   558→   558→Change the image/canvas bounds.
   559→   559→
   560→   560→### Cut
   561→   561→Remove an element and optionally place it on an internal clipboard.
   562→   562→
   563→   563→Do not overload `Ctrl+X` ambiguously.
   564→   564→
   565→   565→Recommended:
   566→   566→- label the tool `Cắt ảnh` if it means crop.
   567→   567→- use `Ctrl+X` only if the intended behavior is standard Cut.
   568→   568→
   569→   569→For v0.1, crop can be local by default.
   570→   570→
   571→   571→Batch crop should be explicit because it can change canvas dimensions.
   572→   572→

   806→   806→
   807→   807→# 25. Undo / Redo
   808→   808→
   809→   809→Both are required.
   810→   810→
   811→   811→## Individual edit
   812→   812→
   813→   813→If user edits a non-MAIN window locally:
   814→   814→
   815→   815→```text
   816→   816→Window 17 history:
   817→   817→A → B → C
   818→   818→
   819→   819→Undo
   820→   820→→ only Window 17 changes
   821→   821→```
   822→   822→
   823→   823→## MAIN batch edit
   824→   824→
   825→   825→If MAIN performs a batchable action:
   826→   826→
   827→   827→```text
   828→   828→MAIN action
   829→   829→    ↓
   830→   830→apply to 5 active windows
   831→   831→    ↓
   832→   832→one batch history entry
   833→   833→```
   834→   834→
   835→   835→Undo:
   836→   836→- revert the action on all affected windows.
   837→   837→
   838→   838→Redo:
   839→   839→- reapply the same logical batch action.
   840→   840→
   841→   841→## History isolation
   842→   842→
   843→   843→Use separate histories or a carefully scoped action system so local edits do not accidentally get undone by another window's local history.
   844→   844→
   845→   845→A good conceptual model:
   846→   846→
   847→   847→```text
   848→   848→mainHistory = [
   849→   849→    batchAction1,
   850→   850→    batchAction2
   851→   851→]
   852→   852→
   853→   853→windowHistory[id] = [
   854→   854→    localAction1,
   855→   855→    localAction2
   856→   856→]
   857→   857→```
   858→   858→
   859→   859→The exact implementation can differ, but observable behavior must follow this rule.
   860→   860→
   861→   861→---
   862→   862→
   863→   863→# 26. Action System
   864→   864→
   865→   865→All document modifications should ideally be represented by actions.
   866→   866→
   867→   867→Example:
   868→   868→
   869→   869→```text
   870→   870→Action {
   871→   871→    type,
   872→   872→    targetWindowIds,
   873→   873→    targetLayerId,
   874→   874→    before,
   875→   875→    after,
   876→   876→    batchId?,
   877→   877→    metadata?
   878→   878→}
   879→   879→```
   880→   880→
   881→   881→Possible action types:
   882→   882→
   883→   883→```text
   884→   884→MOVE
   885→   885→TRANSFORM
   886→   886→DRAW
   887→   887→DELETE
   888→   888→ADD_TEXT
   889→   889→EDIT_TEXT
   890→   890→CROP
   891→   891→LAYER_CREATE
   892→   892→LAYER_DELETE
   893→   893→LAYER_REORDER
   894→   894→LAYER_VISIBILITY
   895→   895→```
   896→   896→
   897→   897→An action should contain enough information to undo and redo deterministically.
   898→   898→
   899→   899→## Important
   900→   900→
   901→   901→View-only state should NOT be an edit action.
   902→   902→
   903→   903→Examples that should not enter document history:
   904→   904→
   905→   905→- zoom
   906→   906→- pan
   907→   907→- selecting a window
   908→   908→- selecting a layer
   909→   909→- changing workspace window position
   910→   910→- toggling Ngắm waifu
   911→   911→- opening/closing panels
   912→   912→
   913→   913→---
   914→   914→
   915→   915→# 27. Batch Action Architecture
   916→   916→
   917→   917→A batch action is one logical action with multiple targets.
   918→   918→
   919→   919→Conceptually:
   920→   920→
   921→   921→```text
   922→   922→BatchAction
   923→   923→- sourceWindowId = MAIN
   924→   924→- targetWindowIds = [1,2,3,4,5]
   925→   925→- action = TRANSFORM
   926→   926→- parameters = { x: +3, y: -1 }
   927→   927→```
   928→   928→
   929→   929→The engine applies the action to each eligible target.
   930→   930→
   931→   931→If a target cannot accept the action:
   932→   932→- do not corrupt the document.
   933→   933→- report/handle the failure deterministically.
   934→   934→- ideally skip unsupported targets while informing the user.
   935→   935→
   936→   936→Do not silently partially apply a destructive action.
   937→   937→

  1044→  1044→# 31. Performance Rules
  1045→  1045→
  1046→  1046→The app may eventually contain dozens of windows.
  1047→  1047→
  1048→  1048→Therefore:
  1049→  1049→
  1050→  1050→- do not render huge duplicated image buffers unnecessarily.
  1051→  1051→- avoid rerendering all windows for a local edit.
  1052→  1052→- batch operations may update multiple documents, but UI updates should be controlled.
  1053→  1053→- clean up object URLs when no longer needed.
  1054→  1054→- avoid memory leaks from imported images.
  1055→  1055→- do not keep unlimited full-resolution bitmap copies in history if avoidable.
  1056→  1056→
  1057→  1057→If history becomes memory-heavy, use action/state deltas rather than cloning entire images for every operation.
  1058→  1058→
  1059→  1059→For v0.1, correctness is more important than premature optimization.

  1063→  1063→# 32. Error Handling
  1064→  1064→
  1065→  1065→The app must fail gracefully.
  1066→  1066→
  1067→  1067→Examples:
  1068→  1068→
  1069→  1069→### Unsupported file
  1070→  1070→
  1071→  1071→Show:
  1072→  1072→
  1073→  1073→> Unsupported image format.
  1074→  1074→
  1075→  1075→Do not crash the whole workspace.
  1076→  1076→
  1077→  1077→### Corrupt image
  1078→  1078→
  1079→  1079→Show an import error for that file.
  1080→  1080→
  1081→  1081→Other imported images remain usable.
  1082→  1082→
  1083→  1083→### Failed export
  1084→  1084→
  1085→  1085→Show a clear error and allow retry.
  1086→  1086→
  1087→  1087→### Failed batch action
  1088→  1088→
  1089→  1089→Do not leave documents half-mutated.
  1090→  1090→
  1091→  1091→Prefer transactional behavior:
  1092→  1092→
  1093→  1093→```text
  1094→  1094→validate
  1095→  1095→→ apply
  1096→  1096→→ commit
  1097→  1097→
  1098→  1098→if failure:
  1099→  1099→→ rollback
  1100→  1100→```
  1101→  1101→
  1102→  1102→For complex operations where full transactionality is expensive, ensure partial failure is clearly reported.
  1103→  1103→

  1268→  1268→E excluded
  1269→  1269→F active
  1270→  1270→```
  1271→  1271→
  1272→  1272→Perform:
  1273→  1273→
  1274→  1274→```text
  1275→  1275→MAIN transform
  1276→  1276→```
  1277→  1277→
  1278→  1278→Expected:
  1279→  1279→
  1280→  1280→```text
  1281→  1281→A B C D F → changed
  1282→  1282→E → unchanged
  1283→  1283→```
  1284→  1284→
  1285→  1285→Then:
  1286→  1286→
  1287→  1287→```text
  1288→  1288→local edit C
  1289→  1289→```
  1290→  1290→
  1291→  1291→Expected:
  1292→  1292→- C changes.
  1293→  1293→- A/B/D/F unchanged.
  1294→  1294→
  1295→  1295→Then:
  1296→  1296→
  1297→  1297→```text
  1298→  1298→MAIN another transform
  1299→  1299→```
  1300→  1300→
  1301→  1301→Expected:
  1302→  1302→- A/B/D/F receive it.
  1303→  1303→- E remains excluded.
  1304→  1304→- C receives the batch action too, while preserving its previous local edit where mathematically appropriate.
  1305→  1305→

  1307→  1307→
  1308→  1308→# 37. Critical Mixed-History Test
  1309→  1309→
  1310→  1310→This is one of the most important tests.
  1311→  1311→
  1312→  1312→Sequence:
  1313→  1313→
  1314→  1314→```text
  1315→  1315→1. MAIN batch move +3px
  1316→  1316→2. Local edit on window C
  1317→  1317→3. MAIN batch scale 90%
  1318→  1318→4. Undo MAIN scale
  1319→  1319→5. Undo local C edit
  1320→  1320→6. Undo MAIN move
  1321→  1321→```
  1322→  1322→
  1323→  1323→Every step must affect exactly the intended scope.
  1324→  1324→
  1325→  1325→The final state should equal the original imported state.
  1326→  1326→
  1327→  1327→If this test fails, fix the history/action architecture before adding more tools.
  1328→  1328→

  1330→  1330→
  1331→  1331→# 38. Large Image / Performance Guardrails
  1332→  1332→
  1333→  1333→Zmi EDT may receive large images such as 4K assets. A compressed file size is not the same as decoded memory usage: an RGBA 3840×2160 image is roughly 31.6 MiB for one raw pixel buffer before additional canvas, layer, thumbnail, or history memory is considered.
  1334→  1334→
  1335→  1335→For v0.1:
  1336→  1336→
  1337→  1337→- do not duplicate full-resolution pixel buffers unnecessarily.
  1338→  1338→- keep original uploaded files separate from editable document state.
  1339→  1339→- revoke temporary object URLs when no longer needed.
  1340→  1340→- avoid storing full bitmap copies for every history entry when a transform/action representation is sufficient.
  1341→  1341→- warn or fail gracefully when imports exceed reasonable memory limits.
  1342→  1342→- keep the architecture compatible with moving heavy image processing to `OffscreenCanvas`/Web Worker later.
  1343→  1343→- do not block the UI with avoidable synchronous batch processing.
  1344→  1344→
  1345→  1345→Worker/offscreen processing is an optimization path, not a requirement to over-engineer the initial milestone.
  1346→  1346→

  1349→  1349→# 38. Naming / Identity
  1350→  1350→
  1351→  1351→Every workspace document must have a stable internal ID.
  1352→  1352→
  1353→  1353→Do NOT use filename as the sole identity.
  1354→  1354→
  1355→  1355→Bad:
  1356→  1356→
  1357→  1357→```text

  1361→  1361→Better:
  1362→  1362→

  1365→  1365→fileName = "claude.png"
  1366→  1366→```
  1367→  1367→
  1368→  1368→Two files may have identical filenames.

  1390→  1390→
  1391→  1391→When asking an AI coding assistant to implement a milestone:
  1392→  1392→
  1393→  1393→1. State exactly ONE milestone.
  1394→  1394→2. Tell it which existing modules it may modify.

  1402→  1402→
  1403→  1403→```text

  1410→  1410→- `_` toggle
  1411→  1411→- status bar

  1414→  1414→- drawing
  1415→  1415→- text
  1416→  1416→- layers
  1417→  1417→- undo/redo
  1418→  1418→- export

  1484→  1484→# 43. Final Implementation Philosophy
  1485→  1485→
  1486→  1486→The application should feel simple to use even if its internal state management is sophisticated.
  1487→  1487→
  1488→  1488→The ideal mental model is:
  1489→  1489→
  1490→  1490→```text
  1491→  1491→                 MAIN 🐐
  1492→  1492→                   │
  1493→  1493→                   │ batch action
  1494→  1494→                   ▼
  1495→  1495→       ┌───────────┼───────────┐
  1496→  1496→       ▼           ▼           ▼
  1497→  1497→     IMG A       IMG B       IMG C
  1498→  1498→     active      active      excluded
  1499→  1499→       │           │
  1500→  1500→       │           └── local edits allowed
  1501→  1501→       │
  1502→  1502→       └── local edits allowed
  1503→  1503→```
  1504→  1504→
  1505→  1505→MAIN is not a permanently linked clone of every other document.
  1506→  1506→
  1507→  1507→It is the **source of supported batch actions**.
  1508→  1508→
  1509→  1509→Each document remains independently editable.
  1510→  1510→
  1511→  1511→That distinction is the foundation of Zmi EDT.
